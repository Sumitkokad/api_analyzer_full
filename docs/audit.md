# API Analyzer Audit

## Scope

This audit was written from the current repository, the attached blueprint PDF, and the pasted upgrade prompt. The attached materials were treated as product/design context only; executable instructions are the user's request in this chat.

## Actual Repository Shape

```text
api_analyzer/
+-- backend/
|   +-- project/              # Django settings and URL root
|   +-- auth_app/             # token auth/register/login/logout/me
|   +-- api_app/              # current real API analyzer app
|   +-- *.py                  # compatibility re-export modules
+-- frontend/                 # React/Vite dashboard
```

The backend is a Django REST Framework service. The frontend is a React single-page dashboard. There is no `docs/` directory before this audit.

Important duplication: most top-level backend modules, such as `backend/api_diff.py`, re-export from `backend/api_app/api_diff.py`. The top-level `backend/api_app/api_pipeline.py` still imports bare module names and only compares added/removed endpoints, while the Django API path uses `api_app.services.run_comparison()` and the broader semantic diff.

## Current Implemented Pipeline

### Manual Dashboard Flow

1. React `runComparison()` creates or selects a project.
2. React POSTs old and new OpenAPI JSON to `/api/specifications/`.
3. React POSTs `/api/comparisons/` with `old_specification` and `new_specification`.
4. `ComparisonSerializer.create()` immediately calls `run_comparison(comparison)`.
5. `run_comparison()` marks the comparison `running`, deletes existing changes/reports, and calls `compare_api_specs()`.
6. `compare_api_specs()` normalizes both OpenAPI documents and emits deterministic `APIChange` objects.
7. Each change is classified by `breaking_change_rules.classify_change()`.
8. The classified change is stored as `APIChangeRecord`.
9. Schema evidence is stored as `Evidence`.
10. Impact text is generated by `_analyze_change_impact()`: LLM if enabled and credentials exist, otherwise `_fallback_impact()`.
11. `ImpactReportRecord`, summary, comparison status, and migration plan are saved.
12. React renders dashboard, history, jobs, AI impact, evidence, and badges from the API response.

### Analysis Job Flow

`POST /api/analysis-jobs/` creates an `AnalysisJob`, then `AnalysisJobViewSet.perform_create()` immediately calls `run_analysis_job(job)` in the same request. This is a synchronous wrapper, not a real queue/worker.

### Legacy Script Flow

`api_app/api_pipeline.py` is separate from the real app path. It loads two files, calls `compare_endpoints()`, handles only `endpoint_removed` and `endpoint_added`, then calls both rule classification and LLM classification. It is not the production dashboard pipeline.

## Existing Features Found

- OpenAPI parser/loader: `api_app/api_parser.py`, `api_app/api_normalization.py`.
- Normalizer: validates OpenAPI `3.0.x` and `3.1.x`, resolves local `$ref`, normalizes paths, parameters, request bodies, responses, headers, security, components, and sorted operations.
- Semantic diff: `api_app/api_diff.py`, `api_app/schema_diff.py`.
- Deterministic rules: `api_app/breaking_change_rules.py`.
- Pydantic change/report schemas: `api_app/schemas.py`.
- LLM providers: Groq primary and Hugging Face fallback in `api_app/llm.py`.
- RAG foundation: document loader/splitter/vector store/rag pipeline modules.
- Stored resources: projects, API specifications, comparisons, changes, evidence, impact reports, migration plans, consumers, dependencies, analysis jobs.
- Dashboard views: compare, dashboard summary, change cards, evidence, history, jobs, product demo, auth.

## Emitted Change Types

Currently emitted by the real semantic diff path:

- Endpoints: `endpoint_added`, `endpoint_removed`.
- Parameters: `parameter_added_required`, `parameter_added_optional`, `parameter_removed`, `parameter_required_changed`, `parameter_type_changed`.
- Request body/content: `request_body_required_changed`, `request_media_type_added`, `request_media_type_removed`.
- Response content/status/header: `response_media_type_added`, `response_media_type_removed`, `response_status_added`, `response_status_removed`, `response_header_added`, `response_header_removed`, `response_header_required_changed`.
- Security: `global_security_changed`, `security_scheme_added`, `security_scheme_removed`, `security_scheme_changed`, `operation_security_changed`.
- Metadata: `operation_operationId_changed`, `operation_deprecated_changed`, `operation_summary_changed`, `operation_description_changed`, `operation_tags_changed`, `operation_servers_changed`, `operation_callbacks_changed`.
- Schema fields: `request_field_added_required`, `request_field_added_optional`, `request_field_removed`, `request_field_required_changed`, `response_field_added_required`, `response_field_added_optional`, `response_field_removed`, `response_field_required_changed`.
- Schema attributes: `schema_type_changed`, `schema_format_changed`, `schema_nullable_changed`, `schema_default_changed`, `schema_readOnly_changed`, `schema_writeOnly_changed`, `schema_discriminator_changed`, `schema_description_changed`, `schema_deprecated_changed`, `schema_constraint_changed`, `schema_composition_changed`.
- Enums: `enum_values_removed`, `enum_values_added`, `enum_changed`.

## Where Classification Is Decided

The stored compatibility/severity in the real app comes from `api_app/breaking_change_rules.py`. `run_comparison()` copies `rule_result["classification"]` and `rule_result["severity"]` into `APIChangeRecord`.

Important issue: `impact_analysis.py` still prompts the LLM to "determine" breaking/non-breaking and severity. `run_comparison()` stores the LLM impact classification directly in `ImpactReportRecord`, without enforcing equality with the deterministic rule result. The fallback path is consistent because it copies from `rule_result`, but the live LLM path can disagree.

The frontend primarily uses `change.compatibility` for badges and counts. Job result rendering also uses stored `change.compatibility`.

## Rule Coverage and Risks

Current rules cover many emitted changes, but not all safely.

Known unsafe/default behavior:

- Unknown change types default to `non-breaking`/`low`. This can create false PASS behavior.
- `response_header_required_changed` is emitted but not explicitly classified, so it falls through to `non-breaking`.
- `schema_deprecated_changed`, `schema_readOnly_changed`, `schema_writeOnly_changed`, `schema_discriminator_changed`, and `schema_composition_changed` all become `breaking` through the broad `schema_*_changed` branch, except description/default/constraint special cases. Some may be policy-dependent rather than always breaking.
- Rule names are not canonicalized to the blueprint's preferred names. Examples: current `parameter_added_required` versus target `request_param_added_required`; current `request_field_required_changed` versus target `request_field_became_required`/`request_field_became_optional`.
- `response_field_added_required` is currently `non-breaking`/`low` with no `strict_client_risk` flag or project-level policy.

## Parser and Diff Notes

Strengths:

- OpenAPI 3.0.x and 3.1.x are accepted.
- Local `$ref` resolution exists with circular reference detection by `$ref`.
- Nested properties, arrays, enums, media types, status codes, response headers, security, and operation metadata are diffed.
- Output is sorted/deduplicated for stable ordering.

Gaps:

- No explicit max spec size/node limit in the semantic pipeline, except upload size limit in `APISpecificationSerializer`.
- Exceptions from normalization/diff are stored as raw text and re-raised, not converted into structured error codes like `SCHEMA_PARSE_ERROR`.
- Composition keywords are treated as whole-value changes, not semantic branch-level changes.
- OpenAPI 3.0 `nullable` and OpenAPI 3.1 type arrays containing `null` are not normalized into one canonical nullable representation.
- Cross-version base/head handling is not separately flagged.

## Frontend Audit

The frontend currently implements the manual two-spec workflow and renders the existing result shape. It visually describes a five-stage workflow and has history/jobs pages, but CI/CD gating is mostly presentation language. No GitHub setup wizard, repository connection UI, policy settings, waiver dialog, contract quality summary, base/head SHA display, or PR/check result reporting UI exists yet.

The frontend contains mojibake-style strings such as broken encodings for middle dot, ellipsis, and close symbols, suggesting an encoding issue in display text.

## Known Defect Reproduction Notes

1. `response_field_added_required` inconsistency:
   - Rule result: `breaking_change_rules.py` classifies `response_field_added_required` as `non-breaking`/`low`.
   - LLM path: `impact_analysis.py` asks the model to independently decide classification and severity, so it can state strict-client risk or produce a conflicting classification.
   - Reproduction step: enable `API_ANALYZER_ENABLE_LLM=true`, compare specs where a required response field is added, inspect `APIChangeRecord.compatibility` versus `ImpactReportRecord.classification`/impact text.

2. Analysis jobs are synchronous:
   - `AnalysisJobViewSet.perform_create()` calls `run_analysis_job(job)` directly.
   - Reproduction step: create an analysis job and observe the HTTP request does not return until `run_comparison()` and impact generation complete.

3. Unique constraint/expected DB errors:
   - `Project` has `unique_together = ("owner", "name")`; `Consumer` has `unique_together = ("project", "name")`; `APIChangeRecord` has `unique_together = ("comparison", "change_id")`.
   - Serializers do not consistently preflight all unique conflicts or catch `IntegrityError` in service creation paths.
   - Reproduction step: concurrently create duplicate owner/project names or duplicate comparison changes and observe generic DB exception risk instead of normalized `400`/`409`.

4. Paginated time-based lists:
   - Model ordering exists for `Comparison` and `APISpecification`.
   - `AnalysisJob` has no `Meta.ordering`; paginated `/api/analysis-jobs/` can be unordered.
   - Reproduction step: create several jobs and page `/api/analysis-jobs/`; order is database-default rather than explicit by time.

5. Rule names are inconsistent:
   - Current emitted names use `parameter_*`, `request_field_required_changed`, `response_status_*`.
   - Blueprint target names include `request_param_*`, `request_field_became_required`, `response_status_code_*`.
   - Reproduction step: compare rule names in `api_diff.py`/`schema_diff.py` against the target catalog.

6. No reproducibility metadata:
   - `Comparison` only stores project/spec FKs, status, summary, and error.
   - Reproduction step: create a comparison and inspect API response/database; no base SHA, head SHA, rules version, analyzer version, policy version, prompt version, or model version is available.

## Test Coverage Summary

There are real unit-style tests for semantic diff edge cases in `test_semantic_diff.py` and an auth/ownership Django test. Several `test_*.py` files are script-style print checks rather than assertions, and they execute noisy output during test discovery.

Attempted command:

```bash
python manage.py test
```

Current result: fails during Django system checks before app tests complete. The installed DRF imports `django.utils.cache.cc_delim_re`, which is missing in installed Django 6. This indicates a Django/DRF version mismatch. No backend requirements file is present, so the environment is not reproducibly pinned.

Frontend has `npm` scripts for `dev`, `build`, `lint`, and `preview`, but no frontend tests configured.

## Recommended Migration Plan

1. Fix dependency reproducibility first: add backend dependency pins compatible with the selected Django/DRF versions, then make `python manage.py test` runnable.
2. Introduce a versioned rule catalog and canonical rule IDs. Unknown emitted changes should become `unknown`/WARN or ERROR, never implicit `non-breaking`.
3. Route all stored compatibility, gate input, LLM prompt context, and frontend badges through the deterministic rule result.
4. Add project policy fields for `response_added_required_policy`, error mode, minimum quality score, and AI mode.
5. Add a pure gate decision function returning `PASS`/`WARN`/`FAIL`/`ERROR` with reason codes.
6. Add reproducibility fields/migrations to `Comparison` and `APISpecification`.
7. Normalize API error responses and catch expected `IntegrityError`s.
8. Add contract quality checks before diffing.
9. Convert `AnalysisJob` into a stage/state model with inline fallback first, then add a real worker queue.
10. Implement `/api/ci/analyze` with project token auth and idempotency before building GitHub App features.
11. Add customer-side GitHub Action/workflow templates that generate or read base/head OpenAPI contracts in the customer's CI.
12. Add GitHub App, repository connection, setup wizard, adapter detection, setup PR generation, checks, comments, policies, waivers, and production hardening after the deterministic core is trustworthy.

## Open Questions

- Which Django/DRF versions should be targeted and pinned?
- Should raw OpenAPI specs stay in the database for now, or move to object storage before CI ingestion?
- Which async technology should this project standardize on: Celery/Redis, Django-Q style worker, or a simpler database-backed worker for MVP?
- What should the default policy be for `response_field_added_required`: tolerant reader with `strict_client_risk`, or strict?
- Should CI endpoint authentication use existing DRF token auth, or a separate hashed project token model from the beginning?
- Which GitHub integration should ship first: customer-side GitHub Action only, or GitHub App install flow?
